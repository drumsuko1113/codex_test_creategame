# Issue #39 API駆動対局 要件定義

## 背景
- 現在の対局進行はフロント内のローカル状態更新が主で、サーバを唯一の正とする構造になっていない。

## 目的
- 着手・投了・局面取得をサーバAPI経由に統一し、同一対局で複数クライアント間の整合性を確保する。

## スコープ
1. 着手API化
- 着手送信は `POST /api/games/{gameId}/moves` を使用する。
- `expectedVersion` を必須送信する。

2. 投了API化
- 投了は `POST /api/games/{gameId}/resign` を使用する。

3. 局面同期
- 初期表示時に `GET /api/games/{gameId}` を取得し、描画状態をサーバスナップショット基準にする。
- 更新時（着手/投了成功時）もサーバ応答スナップショットで状態更新する。

4. 競合時リカバリ
- `VERSION_CONFLICT` 発生時はスナップショットを再取得し、UI整合を回復する。
- クライアントクラッシュを起こさない。

5. ローカル判定依存の撤廃
- ローカルのみで勝敗確定する処理（チェックメイト/千日手/タイムアウトの単独確定）を避け、サーバ応答ベースに統一する。

## 非スコープ
- WebSocketリアルタイム同期
- ポーリング同期（Issue #40）

## 受け入れ条件
1. 着手と投了が必ずAPI経由で実行される。
2. 初期描画と更新描画がサーバスナップショット基準である。
3. `VERSION_CONFLICT` で再取得が走り、局面不整合を回復できる。
4. ローカル `applyMove` 単独更新だけで局面を確定しない。

## TDD方針
1. Red
- APIクライアントに `getGameSnapshot` / `submitMove` / `resignGame` のテストを追加。
- `expectedVersion` と認証ヘッダー送信をテストで保証。
- 終局表示用マッピングのテストを追加。

2. Green
- APIクライアント拡張を実装。
- App の着手/投了/初期同期をAPI駆動へ置換。

3. Refactor
- スナップショット適用処理を関数化し、重複更新を削減。

4. Regression
- `npm test`
- `npm run build`
